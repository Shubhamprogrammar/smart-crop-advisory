# Smart Crop Advisory System — Technical Blueprint

## 1. High-Level Architecture

```
Farmer (mobile/web browser)
        │
        ▼
Next.js Frontend (Vercel)
        │  REST (JWT)
        ▼
Node.js + Express API (Render/DO/AWS)  ──────►  MongoDB Atlas
        │           │                              ▲
        │           ▼                              │
        │        Redis (cache, queues) ◄── BullMQ workers
        │
        ▼  internal REST
Python FastAPI AI Service (Render/DO/AWS)
        │
        ▼
Hugging Face models / scikit-learn / OpenCV / Vector store (MongoDB Atlas Vector Search or Qdrant)
```

Node is the system of record and orchestrator. Python is a stateless inference service — it never talks to MongoDB directly, only receives data in the request and returns predictions.

## 2. Detailed Architecture

- **Sync path** (fast, user-facing): auth, CRUD, dashboard reads, weather (cache-through), crop recommendation, chat — Node calls FastAPI synchronously, gets a response in the request/response cycle.
- **Async path** (slow/heavy): disease image inference, disease-risk batch recalculation, weather sync, market sync, notification fan-out, RAG ingestion — pushed onto BullMQ queues, processed by workers, results written to MongoDB, frontend polls or gets notified.
- **Advisory engine** sits in Node as a rules layer that consumes soil + weather + crop-stage + disease-risk + market data, produces structured recommendations, and optionally calls FastAPI `/ai/chat` only to phrase the explanation in the farmer's language — it never lets the LLM decide the recommendation itself.

## 4. Database Collections & Relationships

- `users` (role: farmer/expert/admin) `1—N` `farms`
- `farms` `1—N` `soilReports`, `1—N` `cropCycles`
- `crops` (reference catalog) `1—N` `cropCycles`, `1—N` `cropCalendars`
- `cropCycles` (a crop planted on a farm for a season) → `1—N` `diseaseDetections`, `1—N` `diseaseRisks`, `1—1` active `cropCalendar` instance
- `cropRecommendations` — snapshot of AI output per farm+season, `N—1` farm
- `diseaseDetections` — `N—1` cropCycle, stores Cloudinary URL + prediction
- `diseaseRisks` — `N—1` cropCycle, computed periodically (BullMQ job)
- `weatherData` — keyed by geohash/lat-lon+date, cached, referenced indirectly via farm location
- `marketPrices` — keyed by crop+mandi+date
- `advisories` — `N—1` farm, generated by advisory engine, has priority/status
- `notifications` — `N—1` user
- `chats` `1—N` `chatMessages` — `N—1` user
- `knowledgeDocuments` — RAG source docs + chunk metadata (vectors in Atlas Vector Search/Qdrant)
- `cropCalendars` — template + per-cycle instance with stage/task status
- `expertCases` `1—N` `expertResponses` — `N—1` farmer, `N—1` expert, `N—1` cropCycle

All collections: `timestamps: true`, soft `status` fields where relevant, compound indexes on (`farmId`, `createdAt`), (`userId`), geospatial index on farm location, text/vector index on `knowledgeDocuments`.

## 5. API Modules (Node/Express)

`/api/auth`, `/api/users`, `/api/farms`, `/api/soil`, `/api/crops`, `/api/recommendations`, `/api/weather`, `/api/diseases`, `/api/advisories`, `/api/irrigation`, `/api/market`, `/api/profit`, `/api/calendar`, `/api/chat`, `/api/notifications`, `/api/expert`, `/api/admin`, `/api/knowledge`, `/health`

Standard envelope: `{ success, message, data }` / `{ success, message, error }` everywhere.

## 6. AI Services (FastAPI)

`/ai/crop-recommendation`, `/ai/disease-detection`, `/ai/disease-risk`, `/ai/soil-ocr`, `/ai/chat`, `/ai/embeddings`, `/health` — each a thin router → service → model/pipeline, stateless, versioned model artifacts loaded at startup.

## 7. RAG Architecture

Ingestion (offline/admin-triggered): PDF/doc → text extraction → clean → chunk (~500 tokens, overlap) → embed (HF sentence-transformers) → store in MongoDB Atlas Vector Search (fallback: Qdrant, no extra DB otherwise). Retrieval: question → embed → vector search top-K → build grounded prompt with strict system instructions (no invented facts, cite uncertainty, no dosages) → HF LLM → answer + sources. Chat endpoint always logs retrieved-chunk provenance for auditability.

## 8. Weather Architecture

Node `weatherService` → checks Redis cache (key: `weather:{lat}:{lon}:{date}`, TTL ~30–60 min) → on miss calls external Weather API → writes `weatherData` + Redis cache. A BullMQ repeating job refreshes weather for all active farm locations periodically and feeds the disease-risk and advisory jobs. Weather API failure → cached/last-known value + graceful "temporarily unavailable" message, never a crash.

## 9. Market Architecture

Similar cache-through pattern: Redis cache + `marketPrices` collection populated by a BullMQ sync job from the market data source. Historical trend = stored time series queried from Mongo. AI-predicted price trends are computed separately and explicitly tagged `source: "ai_prediction"` vs `source: "real_data"` — never merged silently.

## 10. Notification Architecture

`advisories`/disease-risk/weather jobs → `notificationService.create()` → writes `notifications` doc → pushes to a BullMQ `notifications` queue → worker delivers via browser push (core) and optionally email/SMS/WhatsApp adapters (pluggable, off by default). Frontend polls/subscribes for unread notifications.

## 11. Redis / BullMQ Architecture

Redis used for: cache (weather, market, AI chat responses keyed by prompt-hash), rate limiting (sliding window), BullMQ backing store. Queues: `weather-sync`, `market-sync`, `disease-risk-calc`, `notifications`, `ai-heavy` (e.g. disease image inference, RAG ingestion). Workers run in the backend process (or a separate worker process in production).

## 12. Authentication Architecture

JWT access token (short-lived) issued at login/register, bcrypt/argon2 password hashing, `authMiddleware` verifies token, `roleMiddleware(...roles)` gates routes. Passwords never logged/returned. Refresh handled via re-login for MVP (refresh-token rotation can be a stretch goal).

## 13. Role Permissions

- **Farmer**: own profile/farms/soil/crops/disease uploads/chat/advisories/notifications, can create expert cases.
- **Expert**: read assigned/open cases (farmer, farm, soil, weather, disease, AI output), write `expertResponses`, mark resolved. No access to other farmers' data outside assigned cases.
- **Admin**: full read on aggregate/analytics, manage users/crops/diseases/advisory-rules/knowledge base. No direct edit of a farmer's personal farm data outside moderation needs.

## 14. Frontend Pages

Farmer: Dashboard, My Farms (list/add/edit), Soil Health, Crop Recommendation, My Crops (cycles + calendar), Disease Detection (upload/result), Weather, Irrigation, Market, Profitability, Crop Calendar, AI Assistant (chat), Notifications, Ask Expert, Profile. Admin: Dashboard, Farmers, Farms, Crops, Diseases, Advisories, Knowledge Base, Market Data, Analytics, Experts, Settings. Expert: Dashboard, Assigned Cases, Farmer Cases, Recommendations, Profile. Shared: Login/Register, Language switcher, bottom nav (mobile), sidebar (desktop/admin).

## 15. Backend Routes

Mirrors API modules in §5; each route file maps to a controller, each controller calls a service (no business logic in controllers), validators run via middleware before controller.

## 16. AI Endpoints

See §6. Node's `aiClient` service wraps all FastAPI calls with timeout + retry + circuit-breaker-style fallback (return a "temporarily unavailable" structured response rather than throwing to the user).

## 17. External APIs/Services

Weather API (e.g. OpenWeatherMap or similar), agricultural market-price source (e.g. Agmarknet-style API/dataset), OpenStreetMap/Leaflet (no key needed for tiles), Hugging Face Inference API, Cloudinary.

## 21. Team Task Division (3 developers)

- **Dev A — Backend/Platform**: Node/Express core, auth, farm/soil/crop/advisory/profit/market/notification APIs, Redis/BullMQ, security, deployment of backend.
- **Dev B — AI/ML**: FastAPI service, crop recommendation model, disease detection model, disease-risk logic, OCR, RAG pipeline, Hugging Face integration.
- **Dev C — Frontend**: Next.js app, all farmer/admin/expert pages, design system implementation, i18n, charts/maps, API integration, mobile polish.

## 22. Risks & Fallback Plans

- Weather/market API rate limits or downtime → Redis cache + last-known-good fallback + clear "temporarily unavailable" UI state.
- Hugging Face inference latency/cost → move disease detection to BullMQ async job with polling; cache repeated chat prompts.
- Vector search unavailable in chosen Mongo tier → fall back to Qdrant.
- Model accuracy is genuinely limited (small dataset) → always show confidence, degrade to "consult an expert" path below a threshold, never fabricate certainty.
- Time pressure → MVP-first ordering (see §23) so the demo flow works even if advanced features are trimmed.

## 23. MVP vs Advanced Features

**MVP (must work for demo):** auth, farm CRUD, soil entry, weather fetch+cache, crop recommendation, crop calendar creation, disease image detection (limited crop set), disease risk (rule-based minimum), advisory engine (rules-based), basic chat assistant with RAG in English+Hindi, profit calculator, market price display, farmer dashboard, expert escalation (create case).

**Advanced/stretch:** Marathi/Gujarati full coverage, OCR soil report upload, SMS/WhatsApp notifications, admin analytics dashboards, IoT irrigation hooks, dark mode, refresh-token rotation, full test coverage, Docker/deployment automation, monitoring.

## 24. Deployment Architecture

Frontend → Vercel (auto-deploy from `main`). Backend → Render/DigitalOcean/AWS as a persistent Node service + separate worker process for BullMQ. AI service → Render/DigitalOcean/AWS, CPU inference or HF hosted inference API. MongoDB → Atlas (also hosts Vector Search). Redis → Redis Cloud. Cloudinary for all images. Each service exposes `GET /health`. CORS locked to the deployed frontend origin in production.

## 26. UI/UX Design System Summary

- **Palette**: primary sage/leaf green (growth), secondary warm gold/amber (highlights/alerts), neutral off-white/light-gray background; semantic set — success green, warning amber, danger red/terracotta, info sky blue. High-contrast for outdoor sunlight use.
- **Typography**: Inter or Manrope for Latin script + a clean Devanagari/Gujarati-capable pairing (e.g. Noto Sans Devanagari/Gujarati); 4–5 size scale (display/heading/subheading/body/caption); base size slightly larger than typical SaaS.
- **Components**: rounded cards, one consistent radius + single-level soft shadow, filled/rounded icon set, bottom nav on mobile (Dashboard/My Farms/Assistant/Market/Profile), one dominant CTA per screen, glanceable big-number stats, designed empty/loading/error states.
- **Layout**: generous whitespace, one visual hierarchy per screen, 44px+ tap targets, no complex gestures, consistent spacing scale.
